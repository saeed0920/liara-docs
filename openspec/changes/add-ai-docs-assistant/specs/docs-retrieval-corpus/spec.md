## Purpose

Define secure retrieval and reproducible corpus behavior that returns trusted, request-scoped documentation sources with valid site metadata.

## ADDED Requirements

### Requirement: Authenticated retrieval-only engine contract
The engine SHALL expose `POST /retrieve` for retrieval without LLM completion. Its JSON request MUST contain `query`, `page_path`, and `limit`; unknown fields MUST be rejected, `query` MUST satisfy a fixed engine query-length limit, and `limit` MUST be between 1 and 5. The JSON response MUST contain `insufficient_context` and `sources`; each source MUST contain request-scoped `id`, `title`, `url`, `anchor`, `filename`, `startLine`, `endLine`, and `text`. `/retrieve`, `/query`, `/ingest`, and `/documents` MUST require a valid bearer engine token, while `/health` SHALL remain public. The browser MUST NOT call an engine endpoint, and engine CORS MUST NOT permit browser access. Engine-owned completion through `/query` MUST be removed after retrieval parity so Next.js remains the only completion owner.

#### Scenario: Authorized retrieval
- **WHEN** Next.js sends `POST /retrieve` with a valid bearer token, bounded query, internal page path, and `limit` from 1 through 5
- **THEN** the engine returns retrieval-only JSON containing `insufficient_context` and no more than the requested number of fully described sources

#### Scenario: Missing engine token
- **WHEN** a caller requests `/retrieve`, `/query`, `/ingest`, or `/documents` without a valid bearer token
- **THEN** the engine rejects the request without revealing corpus data or performing the operation

#### Scenario: Invalid retrieval schema
- **WHEN** a retrieval request has unknown fields, exceeds the fixed query-length limit, or uses a limit outside 1 through 5
- **THEN** the engine rejects the request before searching the corpus

### Requirement: Bounded independent hybrid retrieval
The engine MUST produce dense and corpus-wide lexical candidates independently before fusion or reranking; lexical scoring only over dense candidates MUST NOT satisfy this contract. It MUST consider at most 8 retrieval candidates and return at most 5 output sources. A versioned relevance threshold MUST determine `insufficient_context`, and the engine MUST NOT force a source for an unrelated query. Duplicate, empty, and out-of-corpus sources MUST be removed.

#### Scenario: Hybrid candidate generation
- **WHEN** a query has distinct lexical and semantic matches
- **THEN** the engine independently obtains both candidate sets, fuses or reranks at most 8 candidates, and returns at most 5 valid sources

#### Scenario: Unrelated query
- **WHEN** all candidates fall below the active versioned relevance threshold
- **THEN** the engine returns `insufficient_context: true` without forcing an unrelated source

### Requirement: Trusted source identity and metadata
Source IDs MUST be generated by the server, MUST be limited to the current request, and MUST NOT be reused as cross-request authority. Source titles, internal URLs, and real MDX anchors MUST come from ingestion metadata generated with the documentation build; neither the retrieval engine nor the LLM may guess or generate URLs or anchors. Returned URL and anchor validity MUST be 100 percent against the corresponding built documentation routes and sections.

#### Scenario: Source metadata is returned
- **WHEN** a corpus chunk is selected as a source
- **THEN** its response ID is request-scoped and its title, URL, and anchor match the trusted manifest for that exact build

#### Scenario: Metadata cannot be validated
- **WHEN** a candidate has an empty, duplicate, out-of-corpus, or non-manifest URL or anchor
- **THEN** the engine excludes it from output rather than guessing replacement metadata

### Requirement: Reproducible corpus manifest
The production corpus MUST be built from `public/llms/**/*.md` and the same documentation build's versioned manifest. The manifest MUST contain `filename`, `title`, `url`, heading text, and the real MDX anchor, and the collection manifest MUST additionally identify the embedding provider, model, dimension, chunker version, corpus commit, and timestamp. If source MDX is used because the primary conversion path is unavailable, it MUST use a separate fallback namespace with no collisions. Hash-based skipping MUST be valid only within the same collection-manifest version.

#### Scenario: Corpus and metadata are reproducible
- **WHEN** a release corpus is generated
- **THEN** its documents and route/anchor metadata come from the same build and its collection manifest records all provider, model, dimension, chunker, commit, and timestamp fields

#### Scenario: Fallback source namespace is used
- **WHEN** the primary Markdown conversion is unavailable and source MDX is ingested as fallback
- **THEN** fallback content occupies a separate collision-free namespace and does not masquerade as the primary corpus

### Requirement: Safe ingestion and stale-content handling
Ingestion MUST preserve changed-content hashing and stale-file deletion, but a missing or empty corpus, a corpus/manifest mismatch, or an embedding-dimension mismatch MUST fail before any deletion or active-collection mutation. Production ingestion MUST run as a release operation rather than as a query-service startup reindex, and document-writing endpoints MUST NOT be exposed to the public network. `ENGINE_PROVIDER=mock` MUST be forbidden in production.

#### Scenario: Corpus mount is empty
- **WHEN** ingestion starts with a missing or empty corpus
- **THEN** ingestion fails before stale-file deletion and leaves the active collection unchanged

#### Scenario: Embedding dimensions do not match
- **WHEN** generated vectors do not match the collection's declared dimension
- **THEN** ingestion fails before deleting or replacing active data

### Requirement: Versioned collection replacement and rollback
Changing the embedding model, embedding dimension, or chunker version MUST create and fully reindex a newly versioned collection rather than modify the existing collection in place. Replacement MUST ingest and evaluate the new collection before atomically moving the active alias; it MUST NOT update the active collection with delete-then-upsert. Required payload indexes, including filename and URL, MUST exist. Qdrant data MUST use persistent storage, and the previous alias target MUST be retained for rollback.

#### Scenario: Incompatible corpus version is deployed
- **WHEN** the embedding model, dimension, or chunker version changes
- **THEN** the system builds and evaluates a new collection before atomically switching the active alias

#### Scenario: New collection fails evaluation
- **WHEN** a newly ingested collection does not pass retrieval evaluation
- **THEN** the active alias remains on the previous persistent collection

### Requirement: Retrieval readiness and evaluation
Public health/readiness output MUST report Qdrant connectivity and active collection existence separately. Retrieval release evaluation MUST use a versioned set of at least 30 Persian and English questions covering exact keywords, colloquial Persian, typos, page context, insufficient context, and prompt injection. Release MUST require recall at 5 of at least 80 percent, URL validity of 100 percent, anchor validity of 100 percent, and abstention precision of at least 95 percent for insufficient-context questions.

#### Scenario: Qdrant is reachable but collection is absent
- **WHEN** Qdrant connectivity succeeds but the configured active collection does not exist
- **THEN** readiness reports connectivity and collection existence as separate results and does not report retrieval as ready

#### Scenario: Retrieval candidate is evaluated for release
- **WHEN** a collection is proposed as the active release collection
- **THEN** it is eligible for alias activation only after the versioned dataset meets the stated recall, URL, anchor, and abstention gates
